# Caster — the design record

Numbered propositions, each with the measurement or the reason it rests on. The brief is [PLAN.md](PLAN.md); the experiments this package ports are `browser-to-pdf-experiments`, and where this file and that repository disagree, PLAN.md §1's precedence decides and the correction is recorded here.

Two headings: **The spine** is Agent A's (the package, the registry, the host, the Cicero adapter, measurement, fonts, emission, the panel); **Painting** is Agent B's. Both are numbered in one sequence per heading.

## The spine

**S1 — fontkit's browser bundle has NO default export; the named `create` is the door.** Measured in a tab (`test/vendor-bundles.test.js`): `import('/vendor/fontkit.js')` gives `create: function` and `'default' in namespace === false`. The harness's `fontkit.d.ts` declares a default because Vite's interop synthesised one; a plain browser module graph gets none, so every port site that read `fontkit.create(...)` off a default import reads it off the namespace here.

**S2 — the two Emscripten glues' node branches are dead in a tab, and esbuild only needs something to resolve.** `harfbuzzjs/dist/harfbuzz.js` and `lcms-wasm/dist/lcms.js` both name `module`, `fs` and `path` inside a branch guarded by `ENVIRONMENT_IS_NODE = typeof process == "object" && process.versions?.node && process.type != "renderer"` — false in a tab. `scripts/bundle-vendor.js` aliases the three to `scripts/vendor-stubs/node-absent.js`, whose every export throws; the tab proof imports both bundles with zero page errors, so nothing reaches a stub. This is the same shape as `editing-tools`' `scripts/bundle-pug.js`, whose stubs are also for a path BelType never takes.

**S3 — both glues locate their `.wasm` beside the bundle through `import.meta.url`, and esbuild preserves it.** `vendor/harfbuzz.js` and `vendor/lcms.js` each carry `import.meta.url` and the literal `"harfbuzz.wasm"` / `"lcms.wasm"`. `harfbuzzjs/dist/index.mjs` runs `init(await createHarfBuzz())` at module TOP LEVEL, so a resolved `import()` of the bundle is itself the proof that the wasm beside it was fetched and instantiated — measured in the tab. The consequence for the registry: `harfbuzz` needs no `wasm` entry of its own; the file is a build artifact of the bundle, not a fetch the registry makes.

**S4 — `harfbuzz-subset.wasm` is not glue-bound: 622 493 bytes, ZERO imports, exporting `hb_subset_or_fail`.** Measured with `WebAssembly.compile` + `WebAssembly.Module.imports()` in the tab. That is why the registry's `hbSubset` entry is a `wasm` file it fetches rather than a module it imports, and why `fonts/hbSubset.js` can instantiate it with no import object — the harness does exactly this. The byte count matches the guide's dependency table.

**S5 — `npm run check` types Caster's own files and stops there.** `checkJs` follows imports, and `packages/common` is plain JavaScript with no JSDoc, so its implicit `any`s arrived as Caster's errors. `jsconfig.json` maps `@egildo/beltype-common/*` to `types/beltype-common.d.ts` (a hand-written declaration of the error hierarchy) and sets `maxNodeModuleJsDepth: 0`. The alternative — annotating `packages/common` — is a change to a package this round does not own, for a benefit this round is the only customer of.

**S6 — the capability registry NEVER falls back, and that is the whole point of it.** `capability(name)` throws a `CapabilityError` naming the capability and the flag that would have loaded it. The reason is measured and is not about tidiness: `docs/guide/shaping.md` §"The two tiers" records that fontkit produces the RIGHT WIDTHS and the WRONG GLYPHS on two of its three failure modes, so a pipeline that fell back when harfbuzzjs failed to load would pass every width assertion in the suite and show the wrong letters on the page.

**S7 — `colour` is Caster's own flag and is the one row the guide's table does not have (D8).** `'auto'` writes E8's objects — `/DefaultRGB`, `/OutputIntents`, the two ICC profiles — exactly when the document declares a `--pdf-*` colour hint, or `blackText`/`convertRgb` is set. PDF/UA-2 does not require them (E5 was clean without), and fetching 192 kB of profiles for a document with no colour story is the download the registry exists to avoid. `'on'` and `'off'` are the operator's override.

**S8 — `.wasm` joins `packages/common/src/mime.js`.** One line, `application/wasm`. Two capabilities are wasm files a host must serve with a type the browser accepts for `WebAssembly.instantiateStreaming`; the table already claims to be the one answer on every path, and `application/octet-stream` was the wrong one.

### The Cicero adapter, measured (§5)

Every claim below was measured in Chromium 141.0.7390.37 against a real `--engine cicero` run of a five-page A4 document whose venue sheet declares `@page { size: A4; margin: 20mm; --pdf-bleed: 3mm; --pdf-trim-inset: 6mm; --pdf-marks: crop cross }`, before the adapter was written. The probe was thrown away; the numbers are here.

**S9 — R1 holds and its generalisation is necessary: Cicero's pages stack VERTICALLY.** Measured page rectangles, first three: `left` 203.156 on all three, `top` 24 / 1161.516 / 2299.031, each 793.688 × 1121.516. The harness's `pageIndexAt(viewportX)` reads x alone and would put every rectangle of the document on page 1. `coordinates/frame.js`'s lookup answers with the page whose rectangle CONTAINS the point, falling back to the last page starting at or before it in y and then in x, with the harness's own 0.01 px tolerance. The one-argument call still answers by x alone, so nothing E10 measured changes shape.

**S10 — R2 holds exactly, and the one-pixel inset is real.** `page.style.width` reads `793.701px` and `page.style.height` reads `1121.52px`; `chase.js`'s `applyConditions` writes `pageH − 1` as a print-safety inset inside the bottom margin track (the fifth grid row measured `74.5906px` against the other four margins' `75.5906px`). So the nominal size is `parseFloat(style.width)` and `parseFloat(style.height) + 1`, and at 0.75 pt/px that is **595.276 × 841.89 pt** — A4 by definition. The MEASURED border box is `793.688px`, Blink's 1/64 px grid, which at 0.75 converts to 595.266 pt and would write a page ten thousandths of a point short; E10's whole argument for a nominal page box reproduced on Cicero's own numbers.

**S11 — R7 is REFUTED on both of the roads it names, by one measurement: Chromium's `@page` parser DISCARDS a custom property.** A constructed sheet whose text is `@page { size: A4; --pdf-bleed: 3mm; margin: 1cm }` serialises back from the CSSOM as `@page { size: a4; margin: 1cm }`; `rule.style.getPropertyValue('--pdf-bleed')` is the empty string, and iterating `rule.style` lists only `size` and the four margin longhands. Registering the property with `CSS.registerProperty` FIRST changes nothing — the same sheet still parses to `@page { size: a4 }`. So the declaration never reaches the CSSOM at all, which closes R7's first road (read it off the page element, where it computed to the initial value `0px`) and its second (read the `CSSPageRule`s ourselves, where there is nothing to read).

**S12 — the decision S11 forces: the page-level `--pdf-*` properties are read from the DOCUMENT ROOT.** `:root { --pdf-bleed: 6mm }`, registered `syntax: '<length>', inherits: false`, computes on `document.documentElement` to `22.6772px` — the guide's own frozen number, arrived at independently — and `inherits: false` keeps it off `body` (`0px`) and off the page host (`0px`), which is exactly the semantics `docs/guide/README.md` §"The registered `--pdf-*` properties" asks for: a declaration claims one element and never its subtree. The author writes it in the venue's own sheet, beside the `@page` rule it belongs with. **Named pages, `:first` and parity are NOT honoured this round**, and the reason is Chromium's parser rather than a choice: there is no channel in which a per-page hint could be written. This is the first item of "What Cicero should stamp" that a Cicero change could actually retire — a `data-pdf-bleed` on the page host, written from a declaration the engine's own capture would have to read out of `@page` before Chromium's parser gets it, which the capture already does for `size` and the margins.

**S13 — R3 holds, and what it assigns is coarser than the harness ever met.** `page.querySelector(':scope > slot').assignedNodes()` answers with the page's flow in order. On a BelType document that flow is `["section"]` — ONE node — because the belt's `sections` plugin (LAST in the chain) wraps the whole document in nested `<section>` elements, so a five-page document is one top-level block that straddles four cuts. Every consequence of R4 and R5 therefore operates on sections rather than on paragraphs, and the walk that finds the content is the walk INSIDE the assigned node.

**S14 — R4 holds: a continuation clone carries no link back to its source.** The clone's attributes are exactly `data-beltype-fragment`, `class` (`__beltype-cont`), `aria-hidden` and `style`; no expando, no id, no dataset entry names the original. `mutateToContinuation` takes `source` and uses it only to read a computed style (`applyCarriedRemainder`). `data-beltype-pos` would ride across on `cloneNode` — it read `null` in the probe because a plain dev server does not ask the belt to stamp, and the editing tools' host does (`new Pipeline(..., { stamp: true })`), which is the one road on which the pos-matching half of R4's pairing rule can fire at all.

**S15 — R5's content area is exactly where R2 says it is.** `.content-area`'s border box sits at (75.578, 75.578) page-local with `overflow: clip`, against a declared 20mm margin of 75.5906px — the difference is the same 1/64 px quantisation S10 names, and it is why the clip is computed from the MEASURED rectangle rather than from the declared margin. `p0.shadowRoot` holds sixteen `.margin-cell` elements on every page whether or not any of them carries text (R6), so the artifact walk is over the cells that have content rather than over the cells that exist.

**S16 — the page host's shadow adopts NO sheet when the author's `@page` declares nothing Cicero does not own.** `page.shadowRoot.adoptedStyleSheets` was empty on this document: the capture takes `size` and the margins for itself and `dress(null)` clears the sheet. So an adapter that read the page's own adopted sheets for anything would read nothing on the common case, and S12's root road is the only one that carries a value at all.

## Painting

*(Agent B's; merged from `caster-b`.)*

**P1 — the four `e3-fixture.ts` constants get a home of their own, `coordinates/units.js`, and every no-frame fallback path in the port is kept.** Thirteen ported modules import `PX_TO_PT` from the harness's E3 fixture, and four more want `COLUMN_WIDTH_PX`, `MARGIN_PT`, `PAGE_WIDTH_PT` and `PAGE_HEIGHT_PT`; `PLAN.md` P3 does not port a fixture, so the constants move rather than being restated in five places. Caster never takes the fallback paths those four feed — the Cicero adapter installs a frame and a page geometry before anything is measured, so `pageGeometryFor` and `pageIndexAt` always answer — but the branches stay, because every content stream E3 through E9 measured went through them and a port that cut them would be a port whose output no experiment ever checked. Dead weight with a receipt.

**P2 — `HintParseError` extends Agent A's `ColorHintError` rather than `CasterError` directly.** P5 asks that the harness's named error classes survive with the same names and the same messages; A's `errors.js` already declares a `ColorHintError` for the same family. Putting the harness's name one rung below A's keeps both, and the panel gets the `{ element }` context P5 adds either way.

**P3 — the harness's `readings` field is dropped from `ColorEmitter.finish()`; `registrations` stays.** D7 drops the sidecar's fixture-only fields. `SidecarHintReading` carries a `case` — a fixture case name — and one row per verify item of E8's own fixture; nothing about a real document produces it, and `ReportColor` has no slot for it. `registrations` is a fact about the run (what `CSS.registerProperty` did on this document) and is kept.

**P4 — `parsePath`'s "is not an SVG path command" refusal is unreachable through its own tokeniser.** `tokenize`'s pattern matches the twenty command letters and numbers and nothing else, so `M0 0 X10 10` loses the `X` before the parser sees it and reads `10 10` as an implicit `L`. Ported as written (P1: the port changes no rule the experiments measured) and pinned by `test/vectors.test.js`, which asserts the implicit-lineto rather than a throw. The branch is worth keeping — a tokeniser that grew a case would want it — and the fix, if it is wanted, is one alternative in the pattern and belongs upstream with the experiments' maintainer.

**P5 — `parseMatrix`'s `matrix3d` branch never fires, because the number pattern matches the `3` in the function's own name.** `/-?[\d.eE+]+/g` over `matrix3d(1,2,…)` returns seventeen numbers, not sixteen, so the sixteen-operand branch is skipped and the six-operand one answers with `[3, 1, 2, 0, 0, 3]`. `imagePlace.js`'s `parseTransform` carries the same regex and the same latent defect. Ported as written and pinned by `test/vectors.test.js`; it is latent rather than live because E10's frame refuses a `matrix3d` on the container chain **by name** before any path reaches either function, and because an element's own `matrix3d` is refused by `ctm.js`'s `PerspectiveError`. Anchoring the pattern to the first `(` is the fix, and it belongs upstream.

**P6 — `transparency.js`'s two form builders each carry their own doc comment.** The harness's file has the comment for `form()` — the transparency-group one, `/I true /K false` and why — sitting above `sharedForm()`, which is a plain form and is plain on purpose. Nothing about the code changed; the two paragraphs are beside the methods they describe.

**P7 — `measure/emoji.js` was ported out of §9's order, at item 4 rather than item 7.** `measure/textMeasure.js` (Agent A's) imports it, so until it existed nothing that reached `textMeasure` — which is `imagePlace.js`, and therefore `pathData.js` and therefore every vector module — could be imported in node at all, and the whole painting suite was unrunnable. Porting it early cost nothing and unblocked eleven modules.

**P8 — every heavy library reaches these modules through `capability()`, so each module file evaluates in node with no bundle present.** `png.js` takes `fast-png`'s `decode`, and `imageEmbed.js`, `shading.js`, `transparency.js`, `vectorEmit.js` and `colorResources.js` take pdf-lib's object layer, each destructured inside the function that writes with it rather than at module scope. That is `PLAN.md` P2's rule, and it is what lets the pure suites read thirteen image fixtures, the whole colour grammar and the whole vector arithmetic without a browser and without a vendor bundle.

**P9 — a `rowspan` reaching past the last declared row throws a bare `TypeError`, and is pinned rather than repaired.** `buildTableModel` grows the grid to hold the span and does not grow `rowList` with it, so the ragged-row padding then looks up a row record that was never made; the harness spells the lookup `rowList.find(...)!`, which asserts the row exists. `<tr><td rowspan="3">` in a one-row table is an ordinary authoring slip and it comes back as a `TypeError` rather than as a `CasterError` naming the cell — the wrong shape for a refusal, by P5's own rule. Ported as written (`PLAN.md` P1) and pinned by `test/tables.test.js`, so the day it is repaired the pin says so. The repair is not obvious enough to make here: a phantom row has no `<tr>`, so what section and what row group it belongs to is a question the experiments never had to answer.

**P10 — the harness's `SidecarComputedBorderWidth` was declared locally in `tableBorders.js` with a `TODO(report)`, and the TODO is now spent.** Agent A's `report.js` carried `ReportCollapsedEdge` and not its neighbour when the tables landed, so §9 item 1's local-declaration rule applied; A landed `ReportComputedBorderWidth` field for field with it in the meantime, and `tableBorders.js` imports it from `../report.js` like every other record type. Nothing about the shape changed at any point.

**P11 — the two refusals ported in items 6 and 7 join the house error family.** `printMarks.ts` throws a bare `Error` for a marks value outside `crop | cross | none`, and `pageLabels.ts` gives `PageLabelParseError` a bare `Error` for a base; here the first is a `CasterError` and the second extends one, the same move `colorHints.js`'s `HintParseError` makes (P2). Both messages are the harness's word for word, and `PageLabelParseError` keeps its `value` field, so what a reader of the message sees is unchanged — what changes is that a refusal from either now carries the `{ element, pos }` context the panel opens a source line from, and that BelType's "every thrown thing is a `BelTypeError` subclass" holds with no exception in this package.

**P12 — the sidecar's two record types are Agent A's report types, taken by their new names.** `SidecarOutlineItem` and `SidecarPageLabel` are `ReportOutlineItem` and `ReportPageLabel` in `report.js`, field for field, so `outline.js` and `pageLabels.js` import from `../report.js` rather than declaring anything locally. Neither needed the `TODO(report)` §9 item 1 offers, because A had landed both before item 7 was reached.

**P13 — the outline suite loads the vendored `pdf-lib` bundle in node and builds a real `PDFContext`.** Every other pure suite here runs with no capability loaded (P8), because every other ported module has a half that computes before it writes. `buildOutline` has no such half: the tree-shaping is four lines and everything else is object construction, so a suite that mocked the object layer would be asserting its own mock. `await load(['pdf'])` in a `before` hook works in node exactly as it does in the tab — the registry imports by `new URL(rel, import.meta.url)` and never by a bare specifier — so the items, the `/First`/`/Last`/`/Prev`/`/Next` threading, the open `/Count`s and the structure destination are all read back out of a context pdf-lib itself made. `treeOf` and `descendants` stayed module-private as the harness had them; exporting them to test the nesting would have been the same mock by another road.

**P14 — the two ICC profiles are copied from `harness/profiles/`, not re-fetched, and their provenance is checked twice.** `scripts/profiles.sh` is `harness/tools/profiles.sh` with the paths moved and a paragraph added about where `capabilities.js` reads the files from; it verifies the same two SHA-256 sums against the same two pinned `raw.githubusercontent.com` URLs and re-fetches only under `--download`. Beside it sits `test/profiles.test.js`, which asserts the same sums and reads the header fields through the exporter's OWN `iccDeviceClass`/`iccColorSpace`/`iccVersion` — `prtr`/`CMYK`/2.1.0 and `mntr`/`RGB `/2.1.0 — plus the ICC size field against the file length, so a truncated or swapped profile fails `npm test` rather than a RIP. The reason for the second check is that a provenance script nobody runs proves nothing; the reason for reading through `colorResources.js` is that the profiles have to pass the refusals that module makes, not merely be the right bytes. `package.json` gains one script line, `"profiles": "bash scripts/profiles.sh"`, beside `bundle-vendor`.

**P15 — the `profiles` capability cannot load in node, and that is the loader's `fetch`, not the files.** `capabilities.js` reads a `files:` or `wasm:` capability with `fetch(new URL(rel, import.meta.url).href)`, and node's `fetch` refuses a `file:` URL (`TypeError: fetch failed`, node 22.22.2 — measured), so `load(['profiles'])`, `load(['hbSubset'])` and `lcms`'s wasm half are browser-only doors while the `url:`-only capabilities — `pdf`, `fontkit`, `fast-png`, `harfbuzz`'s glue — load in node fine, because those go through `import()`. Nothing is broken by it: the printer runs in a tab. It is recorded because it silently shapes what a pure suite can do — `test/profiles.test.js` reads the two files with `readFileSync` for exactly this reason, and `test/outline.test.js` can load `pdf` only because that capability is an import. The fix, if a headless host ever wants one, is a `file:`-aware read inside `fetchBytes`, and `fetchBytes` is Agent A's.

**P16 — thirteen raster fixtures are copied into `test/assets/`, and six deliberately are not.** `harness/fixtures/img/` holds nineteen; `test/assets/PROVENANCE.md` lists what each of the thirteen proves, records all thirteen SHA-256 sums, and names the six left behind with the reason: `photo.png` (3.8 MB), `lowalpha.png`, `screenshot.png`, `alpha.webp`, `photo.avif` and `anim.gif` carry claims that are *measured in a browser* — a decoded pixel, a canvas route, a quality verdict — and those belong to the acceptance test rather than to a suite that reads headers. The thirteen that came carry claims a header decides, which is the passthrough table's whole argument: `parsePng`, `parseJpeg` and `canPassThroughIdat` never decode, so `test/images.test.js` can settle the table's row for every one of them in node from the bytes alone. The files are copied verbatim rather than regenerated, because `harness/tools/images.mjs` needs `sharp` and a network fetch for `arith.jpg`, and a fixture whose bytes are pinned by checksum is worth more here than one this package can rebuild.

**P17 — the last two `TODO(report)` declarations are spent too, and the record types are one declaration each.** `rgbToCmyk.js` carried `ReportConversionEntry` and `ReportConversion` locally under §9 item 1's rule; Agent A has since landed both in `report.js` and the local pair is gone. Two fields differ and A's are taken as they stand: `target` is `string` where the local one narrowed it to `ColorTarget`, and `mode` admits `'none'` where the local one had only the two conversion routes. Neither loss is real — `ColorTarget` is a union of strings and `convertRgb: 'none'` is the default the option table already carries — and one declaration of a record shape is worth more than a narrowing that lived in the module that fills it.


**P18 — `boundaryPieces` closes the fourth edge on the count, not on its length, which closes Agent A's S21.** A square-cornered box walks three explicit edges and closes on a fourth; the harness pushes that closing piece only where the cursor has not already come back to the start, which is exactly right for a rounded path — its last cubic lands ON the start and a ninth piece would break every index in `borderSidePath` — and drops a real edge for a box of zero HEIGHT, whose fourth edge is degenerate for the same reason. So `{w:100,h:0}` answered three pieces where `{w:0,h:20}`, a rounded `{w:100,h:0}` and every ordinary box answered eight, and `borderSidePath` indexed `outer[7]` and threw. The guard now reads `open || pieces.length === 3`: a rounded path arrives with eight pieces walked and still pushes nothing, and a square-cornered box pushes its fourth edge whether or not it has length. **This is a departure from the byte-faithful port, and it is a gap in the harness rather than a transliteration error** — `harness/src/export/cssBoxes.ts` behaves identically and was never wrong there, because no E9 fixture handed it a zero-height bordered box; an `<hr>` is the element that finds it, and BelType's belt emits those. `test/vectors.test.js` pins the three degenerate shapes under both radii, the piece ORDER (the seventh piece is the left edge, a zero-length line rather than an absence), and all four sides of a flat box closing on an empty region instead of throwing.

## The spine, continued — three findings the round produced outside the ports

**S17 — `fetchBytes` reads a `file:` URL, so a `files:`/`wasm:` capability opens in node too.** Agent B's P15 measured the gap at its source: `capabilities.js` resolves every vendor asset with `new URL(rel, import.meta.url)` and reads it with `fetch`, and node's `fetch` refuses a `file:` URL outright (`TypeError: fetch failed`, node 22.22.2), so `profiles`, `hbSubset` and `lcms`'s wasm half were browser-only doors while the `url:`-only capabilities loaded fine because those go through `import()`. The fix is one branch and it belongs here rather than in each caller: `fetchBytes` reads `node:fs/promises` for a `file:` URL and keeps `fetch` for every other scheme, and a realm that can do neither gets a `CapabilityError` naming the URL and the capability rather than a bare transport failure. The registry's law is untouched — a capability that cannot load still THROWS and never falls back (S6) — and what changes is only that a node-side suite can now open a door the tab always could, which is what a later headless caller will want.

**S18 — two margin boxes on one `@page` crash the Chromium renderer under `--engine cicero`, and the specimen declares one.** Measured 2026-09-07 in Chromium 141.0.7390.37 on a venue holding one `index.md` with a heading and a paragraph: one margin box paginates; a second, in the same grid row or a different one, kills the tab. The same document survives under `site` and under `pagedjs`, so it is Cicero's, and Cicero's `src/` is read-only to this round — so the finding is filed where something can fail rather than worked around silently (`.claude/NEEDED-FIXES.md` §1.4, with the minimal reproduction). The specimen keeps ONE margin box and keeps its `string-set` beside it, so the `@top-center` returns unchanged the day the crash is fixed; a fixture quietly rewritten to avoid a crash is how a crash stops being found.

**S19 — the print frame is a SEPARATE frame, `visibility: hidden` and never `display: none`.** Two facts in one arrangement. Separate, because `prepare()` alters the document — list markers become real elements, `font-synthesis` is refused at the root, four custom properties are registered — and none of that may touch the pane the author is looking at; the frame loads the same Service Worker URL the preview shows, so it sees the same working generation, drafts included, and is discarded after the export. `visibility: hidden` rather than `display: none`, because a `display: none` iframe has no layout at all and every rectangle the printer reads would be zero: painting is what has to be off, not layout. The frame applies no `transform`, no `zoom` and no rotation, which is E10's refusal list given nothing to refuse, and it sits at a fixed 1200×1600 so no page of a common size is ever laid out against a narrower viewport. The cost, accepted and named: Cicero paginates twice per print, because `run()` is not re-entrant and a fresh document per export is the only correct shape.

## The compliance run

**Re-run 2026-09-14, after S40–S46 and the shipped faces:** the specimen prints to 380 579 B, `qpdf --check` clean at PDF 2.0, veraPDF `--flavour ua2` PASS with zero failed rules — the claim stands for the file the printer writes today. The manual (M11) is the next document to put under it.

**S20 — the printer runs in the realm it prints, and the module is injected into the print frame.** Everything the printer does is realm-sensitive — `getComputedStyle`, `document.createElement` for a probe, `Range`, `DOMRect`, `CSS.registerProperty` — and a module imported into the APPLICATION's realm reaches the application's `window` for every one of them while measuring the FRAME's document. Measured 2026-09-07, and it fails at the first step: `beginFrame`'s zoom walk called the app window's `getComputedStyle` with an element belonging to the frame and got `Failed to execute 'getComputedStyle' on 'Window': parameter 1 is not of type 'Element'`. The harness never met it because a fixture and its exporter shared one realm. So `editing-tools/assets/caster-panel.js` injects the module into the frame as a blob-URL module script and reads it back off a global — the arrangement `__beltypeCicero` already has, for the same reason. Two consequences worth naming: the frame is a compiled BelType document whose import map has never heard of `@egildo/beltype-common`, so the application copies its own `@egildo/` prefixes across in a second `<script type="importmap">` (Chromium accepts more than one as long as nothing it adds has already resolved); and D3's promise that the registry works "with no import map at all" is what makes the vendor bundles resolve from inside the frame, because `capabilities.js` asks `import.meta.url` and nothing else.

**S21 — `boundaryPieces` answers THREE pieces for a square-cornered box of zero HEIGHT, where every other box gives eight.** Measured directly: `{w:100,h:20}` → 8, `{w:0,h:20}` → 8, a ROUNDED `{w:100,h:0}` → 8, and `{w:100,h:0}` → 3. `borderSidePath` then indexes `outer[7]` and throws. It is not a port error — `packages/caster/src/vectors/cssBoxes.js` is byte-faithful to `harness/src/export/cssBoxes.ts` here — it is a gap the harness's own fixtures never met, and an `<hr>` is exactly the element that meets it. The walk no longer routes an `<hr>` into `decorated` (it is already painted as its own rectangle by v1's `HR` branch, so collecting it as a decorated box painted it TWICE, and the crash was the louder half of that), but the gap stands for any zero-height bordered box an author writes some other way, and it is Agent B's module to close.
>

Glyph 1751 is one of the nine without one: its `loca` entry is zero bytes long IN THE FILE, before anything subsets it. And fontkit's own layout of `->`, `=>`, `!=` and `<=` opens every one of them on that same glyph. That is how a monospace face builds a ligature — every character but the last becomes ONE deliberately empty glyph so the cell advance is kept, and the LAST character's glyph carries a left side bearing that draws the whole arrow backwards across them. Subsetting `[1751, 841]` out of it gives back a program where 1751 is still empty and 841 still has its outline: the subsetter kept exactly what it was handed.

> **So the check was asking the wrong question.** `missing` was *a used glyph with no outline whose CID maps to some text*, which for a spacer is always true, since the spacer is the cluster start and takes the cluster's text. When nothing is missing the extra parse never happens, and where `profile.subset` is false the two programs are the same object and the set is empty by construction. The message says `…and the face itself draws them`, because that is now the whole claim.

## The Paged.js adapter, measured (2026-09-14)

Numbered S42–S47 on the branch that built it (`claude/caveman-mode-dc9971`), and renumbered S49–S54 when it met `main`, whose own S42–S48 had been written in the meantime (S55).

**S49 — reification is ONE primitive with TWO moments, and `::marker` is keyed on `display: list-item` rather than on the tag.** D9 made materialising the pseudo-painted text one of the print preparation's three jobs, run once, before the engine paginates, over the author's content — `li::marker`, `h2::before { content: counter(h2) ". " }`. That was the whole of the need under Cicero, whose pages carry nothing the author did not write. A paginator that paints text of its own moves the need: Paged.js writes `.pagedjs_margin-content::after { content: counter(page) }` into every margin cell, `[data-footnote-call]::after { content: counter(footnote) }` at every call, and lays each footnote body out as `display: list-item` with `::marker { content: counter(footnote-marker) ". " }` — and none of that exists until the pages do, so a preparation that runs before them sees none of it. `adapters/reify.js` is the job on its own, `reify(doc)`: `prepare` calls it for the first moment, and a host that paginates with such an engine calls it again for the second, over the whole document, after `run()`. Two properties are what make one function serve both. It is WHOLE-DOCUMENT, one walk from `documentElement` in document order carrying the counter scopes, because `counter(page)` on the last page's cell must have seen every `.pagedjs_page { counter-increment: page }` before it — and `getComputedStyle` hands the walk substituted values, so `counter-increment: var(--c)` arrives as `page 1` (measured, `test/reify.test.js`) and `pairsOf` never meets a `var()`. And it is IDEMPOTENT: an element carrying a reified span or the suppress class reifies nothing twice, a reified item is `display: block` and no longer a list item, and a second call over a prepared document answers with empty `markers` and `generated` and leaves the DOM as it found it — measured, so the second moment costs the first nothing.
>
> The marker rule moved from the tag to the display type, and that is the decision rather than a convenience. `::marker` is generated for every element whose computed `display` is `list-item`, and only those: a `<span class="footnote">` a paginator laid out as one gets the same leading `span.marker` an `<li>` does, and an `<li>` an author made `display: inline` for a horizontal nav — which paints no marker — gets none, where the tag rule gave it a bullet. The derivation D9 names is kept for the `normal` case, which is Chromium's answer for every ordinary counter marker: `list-style-type` and the item's ordinal among its list-item siblings, `start`, `reversed` and each `value` honoured, the siblings taken ONCE per parent on first demand because the walk alters each item as it passes and a set read at the second item would no longer hold the first. An `<li>` still reads `list-style-type` off its `<ul>`/`<ol>`, as D9 wrote it; anything else reads its own. A `::marker` whose computed `content` is anything but `normal` goes through the same resolver as `::before` — strings, `counter()`, `counters()`, `attr()` — so the footnote body's number is the walk's counter and not a guess, which is what the old `literalOf` could not do (a counter function fell through to the bullet). Two things follow for the walk: `structure.js`'s `FENote` branch takes a leading `span.marker` as the note's `Lbl` exactly as the `LI` branch does, and the marker span goes BEFORE a `::before` span rather than after it, which is the order of the boxes the browser painted.
>
> One departure from D9's own letter, stated. A `list-style-type` outside the nine names this printer can draw is still a REFUSAL on an `<li>`; on any other element it is a warning and the item is left as it was, marker and `display: list-item` both, for the engine to paint — because a list item that is not an `<li>` is the paginator's furniture more often than the author's, and refusing the whole export on the paginator's choice of `@counter-style` would be refusing on something the author cannot reach.

Every claim below was measured in the pinned Chromium against a real `--engine pagedjs` run of the Caster specimen (nine pages, the `beltype-caster-pagedjs` seat on :48753), before `adapters/pagedjs.js` was written. **S76, amended again 2026-11-07: where CSS paints a box later than the tree reads it, the stream follows the paint.** The stream check, once held on every fixture, found two more pages whose stream reads otherwise than their tree: the inline formula's display formula after the paragraph below it, and the clipped heading after the footnote numbers it heads. Neither is a slotting fault. KaTeX's sheet makes a display formula's `.katex-html` `position: relative`, and the visually hidden heading is `position: absolute`; a positioned box with `z-index: auto` paints in CSS 2.1 Appendix E's step 8, after every in-flow box of its stacking context, and `paintOrderOf` gives it that place. The order is kept, for three reasons. In PDF the stream is the painting order: what is drawn later covers what was drawn earlier, so a stream put into reading order would draw a positioned box under the in-flow ink it covers on the page, which is what positioning exists to do. And a stream reordered only where no ink overlaps would need a geometric test against everything painted between the two places, a second paint order to keep right for a gain only to extractors that go by the stream. So the rule is: **the content stream is CSS's painting order, every page's flow in page order; it reads as the structure tree does wherever CSS paints in tree order, and where it does not, the tree carries the reading.** `streamDifferences` in `test/cast-checks.ts` takes the boxes a page paints later by the start of their text, and `test/acceptance-cast.test.ts` holds every fixture's stream to the tree's order with those boxes after the rest of their page.

The two differ only where a selector depends on the structure the spans change (`:first-child`, a sibling combinator, `:empty`, `:has()`), and there the presented page is the oracle, as it is for the cast road (*on the cast road the oracle is the page Cicero presented*, S91). One write stays inside the walk: a shape marker's probe, because it is what that reading reads. In the same round the walk's addresses are held as well (*an address is counted once*, S92): the walk writes nothing to the tree, so `print()` holds them over the walk, releases them before `inlineSvgImages` and holds them again from the paint order; the walk 3.1 s to 2.3 s. The manual's file is byte-identical to the Press round's once the creation date is masked.

**S98 — A VARIABLE FACE IS PINNED ONCE, AT `finish()`, OVER THE GLYPHS IT USED** (2026-10-31, Egildo's ruling in the optimisation round). A CPU profile of a warm print of the CLI's sample paper put `subsetFace` at 174 ms of ~730 ms, and it was the *instancing*, the `keepEverything` pin of a variable face to one weight and optical size, that cost, not the subset at `finish()` (eleven instances: 162 ms instancing against 8 ms subsetting). The instancing existed so that layout would measure the instance's widths; fontkit already gives those (`getVariation(coords)`, `hmtx` plus `HVAR`), and `/W` has taken fontkit's value over HarfBuzz's wherever they disagreed (S20's invariant that the number laid out is the number written). So `embedFace` pins nothing up front: layout asks fontkit's instance of the source, and `finish()` makes one `hb_subset` call per instance that pins the axes and cuts the used glyphs together (`DOWNGRADE_CFF2` when the source is CFF2). The cut program's `hmtx` is then read back for every used glyph and compared with the advance layout used. **One font unit of difference is allowed**: fontkit rounds the instance's fractional advance and HarfBuzz rounds what it bakes into `hmtx`, and on the paper two of eleven faces differ by exactly one unit on some glyphs (236 against 237, 562 against 561); the old two-step code had the same difference, silently, and `/W` was already fontkit's. More than one unit is refused as a `CasterError` naming the face and the glyph, with no fallback. Measured on the paper, median of five warm runs: emit 250 ms to 117 ms, print 434 ms to 306 ms, total 834 ms to 757 ms; the pin and cut of all eleven instances costs 33 ms. `glyf`, `loca`, `hmtx`, every `/W` and every content stream are byte-identical to the two-step file; `head`, `hhea`, `maxp`, `OS/2` and, in some faces, `GPOS` of the embedded program differ, and `FontBBox` xMin is now the used glyphs' box rather than the whole instance's. **CFF2 is untested**: no variable CFF2 face was available, and HarfBuzz 14.4.0 pins CFF2 without baking `HVAR` into `hmtx`, so the check should refuse such a face where the two-step code printed it (a PDF reader takes `/W` and ignores the program's widths, ISO 32000-2 9.7.4.3). The road measured and refused: cutting the whole-face instances in a pool of workers (the `instancing` flag, a shared `hbSubsetCore`, the compiled module posted once) took the emit from 250 ms to 191 ms and the total from 834 ms to 783 ms, because a cold worker needs 60 to 70 ms for its first instance; it is on the branch `badb4a9` only.

**S99 — THE WIDTHS ARE HARFBUZZ'S, THE SHAPER'S OWN** (2026-10-31, Egildo's ruling after the lazy pin, S98). With S98 the only work left in `embedFace` before `finish()` was fontkit's reading of the widths (`getVariation(coords)`, then `getGlyph(gid).advanceWidth`), while the words had been shaped and measured with HarfBuzz all along. On the paper, summed over the eleven faces, median of five warm runs: `getVariation` 4.6 ms, the 335 first reads of a glyph 20.6 ms (about 61 µs each, with HVAR present in every face, so not the outline-decoding path), `create` 0.5 ms; HarfBuzz's `glyphHAdvance` for all 333 used glyphs takes 0.2 ms. Compared glyph by glyph against the cut program's `hmtx`, HarfBuzz disagreed on none of the 333, and fontkit on six, in two faces, each by one unit (236 against 237, 562 against 561, 625 against 624, 628 against 627, 377 against 376 twice): HarfBuzz rounds the interpolated advance the way it bakes it into `hmtx`, fontkit does not. The effect on the file: the six `/W` entries above move by one unit, and the `TJ` jumps that compensate against `/W` move with them (a word space is one unit wider in `/W` and its jump one unit smaller, so the glyphs stand where they stood, but for a few line starts that move by 0.01 pt where the pen's rounding falls differently); the glyph strings are identical. The road measured and refused: compressing the streams at save time with the browser's `CompressionStream` instead of pdf-lib's pako (flate was 18 ms of a ~710 ms print, 14 in the `flateStream` calls and 4 in the page streams) gave no gain back to back (print 300.8 ms against 299.2 ms) and 483 bytes more; it is on the branch `native-deflate`.

**S99, amended 2026-11-02 (Egildo's ruling for the round *close the display list*, stage 1): the list's widths are the authority, and the builder is the one that asks.** HarfBuzz still answers, at the instance's coordinates and unkerned, and the answer is still the font the words were shaped with; what moved is who asks and where the answer lives. **S100 — `font-kerning: none` AND `text-rendering: optimizeSpeed` REACH THE SHAPER** (2026-10-31, Egildo's go after the Blink probe). ## The standard as a flag (2026-11-03)

Egildo's ninth ruling of 2026-11-03 on the Rust writer (`.claude/plans/the-rust-writer/plan-rust-writer.md` in the BelType monorepo), written first in `codeberg.org/BelType/decisions` as *PDF/UA-2 is a flag, not a given*.

**S103 — PDF/UA-2 IS A FLAG, NOT A GIVEN** (2026-11-03, Egildo's ruling after Typst's `--pdf-standard`, WeasyPrint's `--pdf-variant` and Prince's `--pdf-profile`; the record is *PDF/UA-2 is a flag, not a given* in the decisions repository). **Measured.** The cff2 fixture was HarfBuzz's one-character test subset of Source Serif 4 Variable, a face with no space glyph: `spaceGlyph` shaped U+0020 to glyph 0, the builder wrote `space: 0` on every text item, and forme's file showed `.notdef` in every word gap under a PDF/UA-2 claim, failing ISO 14289-2 8.4.5.9 under veraPDF's `ua2`, `wt1a` and `wt1r` (the oracle refused the list for its `HVAR` widths first, so only forme's file showed it). **The flag.** `standard: 'ua-2' | 'none'`, default `'ua-2'`. Under `'ua-2'` the file claims PDF/UA-2 in its XMP and forme writes both Well-Tagged PDF declarations beside it (stage 10), and a word gap that would be glyph 0 is refused by name: ``caster: the face <family> (<instance>) has no space glyph, so the word gap in text item <n> of page <p> would be glyph 0, .notdef, which PDF/UA-2 forbids a file to show (ISO 14289-2, 8.4.5.9); give the text a face with a space, or print with `standard: 'none'`, which claims no standard and writes the gap as positioning with no glyph``, carrying `listItem`. Under `'none'` the file is tagged as ever and claims nothing, no `pdfuaid` block and no declarations, and such a gap is written as positioning alone: no glyph, the adjustment moving the pen the whole way to where the browser put the next word, and no ToUnicode entry for glyph 0. **How the claim travels.** The display list already carried the claim as data, `info.conformance`, `pdfua2` or `tagged`, and both writers already wrote the XMP from it, so the list stays at version 6 and neither writer reads the flag: `print()` decides `report.conformance` (`tagged` under `'none'` or once a guess was made) and hands it to the builder, whose list records it. The gap rule is `checkGaps` (`displayList/validate.ts`), which the builder calls on the list it made, so the refusal comes before either writer is asked, and `validateList` calls in both writers (forme's `check_gaps`, the same sentence) for a list that reaches them some other way; `emitRun` and forme's `run` write the positioning wherever `space` is 0, which only a list claiming nothing can then hold with a gap. `recordsOf` reports such a gap's `spaceEmitted` as `false`. **Where it meets S90.** *The printer guesses, says so, and withdraws the claim* stays as it is: under `'ua-2'` a guess still withdraws the claim and its declarations, and the report's `conformance` says `tagged`. ## Images may be converted to CMYK (2026-11-04)

**S105 — AN IMAGE IS CONVERTED TO CMYK ONLY WHEN `convertImages: 'cmyk'` ASKS, AND THE LIST IS VERSION 7** (2026-11-04, the second round, brief 4). **The rule it amends.** E7 (`images.md`) and E12E (`colour.md`) said an image is never colour-converted: it is `/ICCBased` sample data under the output intent, and late binding is the default. That stays the default. `convertImages: 'none' | 'cmyk'`, default `'none'`, converts every RGB or grey image to `DeviceCMYK` in the image pass, after the reduction, through the vendored lcms-wasm from the image's own profile (the file's `iCCP` or APP2, else sRGB) to the output intent's CMYK, under the one intent Caster has, relative colorimetric with black-point compensation (ruling 5: no flag), with lcms's default optimisation: **images are optimised and text is exact** (Egildo's ruling of 2026-11-04, after the first build kept the text's unoptimised transform). The text's transform stays `cmsFLAGS_NOOPTIMIZE` (brief 3) because a work list of a few colours costs nothing to evaluate exactly; an image's pixels do, and the optimisation, which resamples the profile onto an eight-bit grid, is about 12 times faster for a mean difference of 0.26 of an eight-bit level and at worst 7 (about 1 in 800 samples is off by more than 2; measured on `convert-images`'s two photographs) (measured below). **What it needs.** The colour objects: with `colour: 'off'` the flag is refused naming both, and with `colour: 'auto'` it turns the colour story on, as `blackText` and `convertRgb` do. **What converts, and what does not.** Eight-bit samples are converted at eight bits and sixteen-bit samples at sixteen and kept at sixteen; the alpha plane is split off, never sent through lcms, and put back beside the CMYK, so it reaches the file as an `/SMask` as any alpha does; an `Indexed` PNG is expanded to its colours (and its `tRNS` alpha) first; a grey image with no profile is read as the grey of sRGB, three equal channels, and one with a grey profile as `TYPE_GRAY`; a profile of the wrong colour space for the pixels, or one lcms cannot open, is refused naming it, since Caster guesses no profile.
